Introduction

What is Open Remote Play?

Open Remote Play (ORP) is a vendor-neutral, open-source protocol standard for low-latency peer-to-peer interactive remote play and controller virtualization.

Decoupled Architecture

Standardizes signaling envelopes, cryptographic handshake, and gamepad packets so any client can talk to any host without custom proprietary code.

Multi-Language Ecosystem

Backed by machine-readable JSON schemas so reference implementations in TypeScript, Rust, Python, and C++ remain 100% intercompatible.

Serverless Rendezvous

Zero central servers needed. Signals race over public Nostr relays, MQTT brokers, and BitTorrent trackers to establish direct P2P connections.

Sub-2-Second Budget

Enforces a strict 2,000ms connection-time budget from initial signaling discovery through first rendered video frame.

Protocol Scope

What ORP Handles

The protocol defines strict wire formats and behaviors for these core responsibilities:

01
Signaling & Discovery
Preflight host discovery (/api/orp/manifest), v2 envelopes, and multi-protocol serverless rendezvous.
02
Fast-Lane Input Transport
Unordered, unreliable UDP-like DataChannel (orp-input) with W3C Gamepad, KBM, and WebHID mapping.
03
Cryptographic Identity & PIN Proof
HMAC-SHA256 signature verification preventing session hijacking without requiring central accounts.
04
Stuck-Input Prevention & Rest States
Mandatory zeroed neutral rest-state packets dispatched on physical disconnect or browser tab blur.
05
Capability Negotiation
Automatic feature intersection (core:* vs ext:*) with silent discard of unknown extensions.
Non-Goals & Boundaries

What ORP Is NOT

To remain lightweight and universally embeddable, ORP deliberately avoids the following:

NOT
A Centralized Platform or SaaS
No login servers, user accounts, cloud databases, or subscription paywalls. Completely self-hosted and P2P.
NOT
A Video Codec or Encoder
ORP does not encode video. It standardizes the data channel and packet headers; what video format rides inside (H264, VP9, AV1) is up to the host.
NOT
A Screen Capture Tool
ORP does not record your screen. The host application captures frames (via PipeWire, DXGI, or Game Engine) and feeds them into the ORP channel.
NOT
A Relayed TURN Network
ORP relies strictly on STUN NAT reflexive discovery and burst hole-punching. It does not run costly middleman relay servers.
NOT
A Proprietary Client Application
It is a standard specification. Anyone can build a client in Flutter, Godot, React, or native C++ under the MIT license.
Quick Start Guide

How to Implement an ORP Client

Build a custom viewer in 5 simple steps:

Step 1 Preflight Discovery

Send GET /api/orp/manifest to fetch the host's session ID, signaling URL, and supported features (core:gamepad, ext:webcodecs).

Step 2 Join Handshake

Connect to the signaling URL and emit a v2 envelope: { v: 2, type: 'join', senderId, sessionId, sig, ts }.

Step 3 WebRTC P2P Exchange

Receive the host's offer, create your WebRTC answer, exchange ICE candidates, and open the connection.

Step 4 Stream Gamepad Telemetry

On DataChannel orp-input, poll controllers at 60Hz and send standard 17-button/4-axis JSON packets.

Step 5 Render Video Stream

Decode video frames from DataChannel orp-video (using WebCodecs VideoDecoder) or from the standard media track.

Quick Start Guide

How to Implement an ORP Host

Turn any game engine or backend into an ORP host:

Step 1 Expose Preflight Manifest

Serve GET /api/orp/manifest declaring your engine name, routing session ID, and capabilities (e.g. ["core:gamepad", "ext:rumble"]).

Step 2 Announce Session

Connect to the signaling server and register: { type: 'host-announce', sessionId }.

Step 3 Create DataChannels

Create orp-input with { ordered: false, maxRetransmits: 0 } to receive zero-latency fire-and-forget inputs.

Step 4 Inject Inputs

Parse incoming JSON packets and inject into virtual controllers via Linux uinput, Windows ViGEmBus, or your game engine's input manager.

Step 5 Multiplex Video Frames

Encode video once using hardware GPU encoding, then broadcast the identical compressed chunks to all connected viewers over orp-video.

Extensibility Note: Unrecognized fields and non-core extensions (e.g. ext:motion) are safely discarded by standard receivers without disconnecting.
